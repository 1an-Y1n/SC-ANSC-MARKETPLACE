# jira-devin-bot

> `ai-toolbox/tools/` 下的一个条目：把 JIRA 变成 AI 的任务队列 —— 工单上有人写 `@AI`，cron 轮询到就驱动 Devin CLI 干活；AI 需要人确认时把问题回写到 JIRA 评论并暂停，人回复 `@AI` 后再续跑**同一个会话**；整个流程跑完自动回写一条任务结论。
> An item under `ai-toolbox/tools/`: turns JIRA into an AI task queue — a human writes `@AI` on a ticket, cron picks it up and drives the Devin CLI. When the agent needs input it posts the question as a JIRA comment and pauses; a human `@AI` reply resumes **the very same session**; a short task conclusion is posted once the whole flow finishes.

> ⚠️ **装进具体项目时需自行指定 skill / pick a skill when you deploy it**
> 本条目是**通用**的：它不绑定任何特定 skill，`config.skill` 由你在装进某个项目时决定（例：装进 `comcast-dz3` 时填 `jira-fix-verify`）。
> 但它**调用的那个 skill 必须存在于目标仓库**（或已安装到 agent 的 skill 目录）——本条目不自带这些 skill。
> This item is **generic**: it binds to no particular skill, and `config.skill` is your per-project choice (e.g. `jira-fix-verify` when deploying into `comcast-dz3`). The skill it names must exist in the target repo (or be installed for your agent) — this item does not ship them.

## 1. 这是什么 / What this is

一个**常驻调度器**：cron 每分钟唤醒一次，轮询 JIRA，发现「**我自己写的、以 `@AI` 开头的评论**」就驱动 Devin CLI 在该工单上干活。

- AI 需要人类输入时，把问题回写到 JIRA 评论并**暂停**；
- 人回复 `@AI` 后，**续跑同一个 Devin session**（上下文完整保留）；
- 整个流程跑完（`[[DONE]]`）后，**再续一次同一 session** 生成一段任务结论并作为**独立评论**发到工单上。

**English.** A long-running scheduler: cron wakes it every minute, it polls JIRA, and a **new `@AI` comment written by the bot's own account** makes it drive the Devin CLI on that ticket. When the agent needs input it posts the question as a JIRA comment and pauses; a human `@AI` reply resumes the **same** Devin session (context intact). Once the flow finishes, it resumes that session once more to produce a short task conclusion and posts it as a **separate comment**.

---

## 2. 为什么值得装 / Why it's worth it

- **把等待人类反馈的漫长空档变成"挂起"而不是"占着一个 session"** —— 阶段做完就退出，人来回复再续跑；
- **上下文不丢**：续的是同一个 session，不是重新开一个；
- **多人可各自部署**：触发器要求「指派给我 + `ai-auto` label + **我自己写的** `@AI`」，所以别人写 `@AI` 不会把我的 bot 也点着；
- **结论一眼可见**：流程跑完自动发一条精简结论，同事不用翻长报告；
- **串行队列**：长任务（编译 / 烧录）运行期间其它工单只入队，不抢资源。

**English.** Turn a long human-feedback wait into a suspend/resume instead of a held session; keep context by resuming the same session; let several people run their own copy safely (the trigger requires the ticket be assigned to you, labelled `ai-auto`, and the `@AI` comment written **by your own account**); get a short, scannable conclusion posted automatically; and keep execution serial so a long build/flash never competes with other tickets.

## 3. 怎么用 / How to use

### 3.1 触发一个工单 / Trigger a ticket

三件事都要满足：

1. 工单**指派给你**（`assignee = currentUser()`）；
2. 工单带 **`ai-auto`** label；
3. 你发一条**以 `@AI` 开头**的评论。

之后 cron 会在 ≤5 分钟内接手。示例：

```
@AI 用 Mamba#1D 这台设备开始修复
```

**English.** All three must hold: the ticket is assigned to you, carries the `ai-auto` label, and you post a comment that starts with `@AI`. Cron picks it up within ~5 minutes.

### 3.2 评论协议 / Comment protocol

| 方向 | 格式 | 判定 |
| --- | --- | --- |
| bot → JIRA | `[Generated by AI]` + 内容 | 前缀匹配 → bot 自己发的，忽略 |
| 人 → bot | `@AI` + 内容 | 前缀匹配 **且作者是 bot 自己的账号** → 触发 |

**两个条件缺一不可**：只看作者不行（bot 与你共用同一账号，bot 的评论作者也是你）；只看前缀不行（多人各自部署时，别人的 `@AI` 会把我的 bot 也点着）。

| 谁写了 `@AI` | 我的 bot | 他的 bot |
| --- | --- | --- |
| 我（我的账号） | ✅ 开工 | ❌ 忽略 |
| 别人（他的账号） | ❌ 忽略 | ✅ 开工 |

**English.** Two conditions, both required: the body starts with `@AI` **and** the comment was written by the bot's own JIRA account. Author-only fails because the bot shares your account; prefix-only fails because several people deploy their own copy.

### 3.4 你会收到通知吗 / Do you get notified

**默认不会。** bot 用的是**你自己的 JIRA 账号**，JIRA 把它的评论视为"你自己发的评论"，而 Jira 默认**不给自己的改动发通知**。

这不只影响进度通知 —— 更要紧的是：AI 卡在 `[[NEED_HUMAN]]` 等你确认时（"用哪台设备""要不要提交 commit"），**你也不会收到邮件**，异步流程会静默停在那里。

所以 bot 会在每条评论开头 @ 你一次：

```
[~11798] [Generated by AI]

**等待人类确认。**（ticket EGS00-996，用时 00:01:37）
...
```

**自我 mention 会强制发通知**（即使"我的改动"设为不通知，Atlassian 已确认该行为）。所以 **AI 的每一条回复都会 @ 一次本 PAT 所属账号**：

- **不是配置项** —— 所有 `[Generated by AI]` 评论一律带 @，包括 `ask_human.py` 发的那条提问（最需要你看到的一条）；
- 实现放在唯一的收口点 **`JiraClient.add_comment()`**，所以以后新增的发评论代码也不会漏。

> **更彻底的做法**：给 bot 一个**独立 JIRA 账号**。那样它的评论来自"别人"，你作为 assignee / watcher 本来就会收到通知，也不必依赖 mention 这个变通 —— 而且通知、审计、作者隔离三件事一起解决。

**English.** By default **you are not notified**: the bot posts with *your* JIRA account, so Jira sees its comments as your own and never mails you about your own changes — which also means a `[[NEED_HUMAN]]` question would sit unnoticed. Every AI comment therefore opens with a mention of the token's own account (`[~11798] [Generated by AI] …`); a self-mention forces a notification even when "my changes" is set to *do not notify* (confirmed Atlassian behaviour). This is **not a config option** — it is applied to every `[Generated by AI]` comment, including the question posted by `ask_human.py`, at the single choke point `JiraClient.add_comment()`. The cleaner long-term fix is a **dedicated JIRA account for the bot**, so its comments come from somebody else and normal watcher/assignee notifications apply.

### 3.3 运行状态 / Runtime status

```bash
./status.sh            # 面板：运行中 / 等待人类 / 队列 / 最近完成
./status.sh --watch    # 每 5s 刷新
./status.sh --stats    # 统计：运行次数、耗时、失败、等待人类
./status.sh --json     # 机器可读
cat STATUS.md          # 状态快照（每轮 tick 刷新）
tail -f logs/cron.log                       # 调度器日志
tail -f runs/<TICKET>/stream.jsonl          # 某工单最新一次运行的实时输出
python3 poll.py --dry-run                   # 看"将要触发哪些工单"，不写任何东西
```

**English.** The commands above cover the live panel, aggregate stats, machine-readable output, the scheduler log, a ticket's live output, and a dry run that changes nothing.

## 4. 一键安装 / One-command install

```bash
git clone http://172.21.1.202:8090/ansc-cas/ai-toolbox.git ai-toolbox
cd ai-toolbox/tools/jira-devin-bot
./install.sh            # 装到 ~/.agents/tools/jira-devin-bot + 装好 crontab + 打印你还要做的四件事
./install.sh --repo /path/to/your/project --skill jira-fix-verify   # 顺便设好 repo_dir / skill
./install.sh --no-cron  # 同上，但不碰 crontab
./install.sh check      # 只检查现状（含安装副本漂移），不改任何东西
```

装完之后，**你要改的 `config.json` 在安装位置**：`~/.agents/tools/jira-devin-bot/config.json`。

`install.sh` 会：校验依赖 → **把载荷装到固定位置 `$HOME/.agents/tools/jira-devin-bot`**（`rsync` 覆盖；`config.json` / `state.db` / `runs/` / `logs/` 受 `--exclude` 保护，重装不会丢）→ 生成 `config.json`（已存在则不动）→ **自动装好 crontab**（指向安装副本，每分钟唤醒一次）→ 打印**自动选中的 devin 路径让你确认**（本机有多个候选时会列出其它的）→ 打印**只有你本人能做**的四件事（设 `repo_dir`、改 `jql`、设 `skill`、填 JIRA 凭证）。

> ⚠️ **装完请扫一眼「devin 用的是」那一行** —— devin 是自动找的，一台机器上可能有多个版本（本机实测就有两个）。不是你要的那个，就在 `config.json` 里显式写 `devin_bin`。

> **代码装在哪**：`$HOME/.agents/tools/jira-devin-bot` —— 与本仓其它条目一致（skill 装到 `~/.agents/skills/<名字>`，gitnexus 的脚本装到 `~/bin`）。crontab 指向的是**安装副本**，所以你 clone 在哪、之后挪不挪都不影响运行。
> **更新代码** = 重新跑 `./install.sh`（覆盖安装；`check` 会检测安装副本与源的漂移）。
> **要改的 `config.json` 是安装副本里的那个**，`install.sh` 会把完整路径打给你。

**前置条件 / Prerequisites**：

| 依赖 | 怎么检查 | 怎么装 |
| --- | --- | --- |
| `python3`（3.8+） | `python3 --version` | `apt-get install python3` |
| `requests` | `python3 -c "import requests"` | `pip3 install requests` |
| `flock` | `which flock` | `apt-get install util-linux` |
| `devin`（Devin CLI，已登录） | `devin auth status` | 见公司 Devin CLI 安装说明。**不是安装的前置条件** —— 找不到 devin 也能装完（config 照生成、crontab 照装），只是调度器在你修好之前不会真正干活；位置也不用你操心，见 `devin_bin` |
| `git` | `git --version` | `apt-get install git` |

**English.** `install.sh` verifies the dependencies (the `devin` CLI is **not** a hard prerequisite: the install completes and `config.json` is seeded even when it is missing, the scheduler just cannot work until you fix it — and its location is auto-detected, see `devin_bin`), **copies the payload to a fixed location** (`$HOME/.agents/tools/jira-devin-bot`, via `rsync`; `config.json` / `state.db` / `runs/` / `logs/` are excluded so a re-install never wipes them), seeds `config.json`, **installs the crontab line** (pointing at the installed copy, waking every minute), prints **the devin binary it picked so you can confirm it** (listing the other candidates when the machine has more than one), and prints the four things only you can do: set `repo_dir`, edit the `jql`, set the `skill`, and provide JIRA credentials. Do glance at that "devin in use" line — devin is auto-detected and a machine may carry several versions; if it picked the wrong one, set `config.devin_bin` explicitly. The cron entry points at the installed copy, so where you cloned does not matter; re-run `./install.sh` to update, and edit the `config.json` **inside the install location** (the installer prints its full path).

### 装完之后必须做的三件事 / Three steps you must do yourself

`install.sh` 生成的只是**模板**，有三处**不改就不会按预期工作**。

#### (1) `repo_dir` —— 调度器在**哪个项目**里改代码

⚠️ 这是**目标项目**的路径，**不是**本工具所在的仓库。本工具是通用的（装在 `ai-toolbox` 里，却要去别的项目干活），所以它**不会也不该**自动猜。**必填**，留空时收到 `@AI` 会直接报错：

```json
"repo_dir": "/path/to/your/project"
```

- 也可以安装时直接给：`./install.sh --repo /path/to/your/project`；
- 例：装进 `comcast-dz3` 时填 `/mnt/home1/.../9409mr2_mamba2/dz3`。

#### (2) `jql` —— 不改就什么都不会触发

`jql` 还是占位值（`YOUR_PROJECT`）。把它改成你自己的项目。推荐写法（**多人各自部署时 `assignee = currentUser()` 是必须的**，否则大家的 bot 会抢同一张工单）：

```
project = EGS00 AND assignee = currentUser() AND labels = ai-auto
```

改完用这条命令验证「将要触发哪些工单」——它不写任何东西、不调 devin：

```bash
python3 poll.py --dry-run
```

> `./install.sh check` 会在 `repo_dir` 为空、或 `jql` 仍是占位值时直接报 `[FAIL]`。

#### (3) `skill` —— 收到 `@AI` 时用哪个 skill 来响应

本工具是**通用的**：它**不绑定任何特定 skill**，而是让你**在装进某个项目时**决定用哪个 skill 来响应 `@AI`。

```json
"skill": "jira-fix-verify"
```

- 填 **skill 名** —— agent 按名字识别并走该 skill 的流程；
- **留空** —— 不指定 skill，只让 agent 自行处理该工单；
- 也可以安装时直接给：`./install.sh --skill jira-fix-verify`。

> 例：装进 `comcast-dz3` 这类固件仓库时填 `jira-fix-verify`；装进别的项目就填那个项目自己的 skill。

（另外还要填 **JIRA 凭证**，见 §5.2 —— `install.sh` 也会把它列成第 4 件事。）

**English.** The generated `config.json` is only a template; three fields must be set before it behaves. **(1) `repo_dir`** is the **target project** — *not* the repo this tool lives in, so it is never derived; it is required, and an `@AI` arriving with it empty fails loudly (`./install.sh --repo <path>` sets it). **(2) `jql`** still holds the `YOUR_PROJECT` placeholder and nothing will ever trigger until you change it — use the shape above, where `assignee = currentUser()` keeps concurrent installs from fighting over the same ticket. **(3) `skill`** names the agent skill that answers an `@AI` comment; this scheduler ships generic, so *you* decide per project (`./install.sh --skill jira-fix-verify` sets it for you). Leave it empty to let the agent decide. JIRA credentials (§5.2) are the fourth thing.

### 怎么让一个任务被调度器认到 / How a ticket gets picked up

三件事**缺一不可**（详见 §3.1）：

| # | 条件 | 说明 |
| --- | --- | --- |
| a | 工单**指派给你** | 对应 JQL 里的 `assignee = currentUser()` |
| b | 工单带 **`ai-auto`** label | 你手动加；**移除 label = 退出管辖** |
| c | 你发一条**以 `@AI` 开头**的评论 | 必须是**你自己账号**写的 |

之后 cron 会在 ≤5 分钟内接手。示例：

```

```

> 别人写的 `@AI` **不会**触发你的 bot —— 那是他自己的 bot 的事（见 §3.2 的隔离表）。

**English.** All three must hold: the ticket is assigned to you, carries the `ai-auto` label, and you post a comment starting with `@AI` — written by **your own account**. Cron picks it up within ~5 minutes. An `@AI` written by somebody else will not trigger your bot.

### 升级 / Upgrade

`install.sh` 是**幂等**的：**重跑就是升级**（载荷整体覆盖）。

```bash
./install.sh upgrade            # 等价于 ./install.sh，只是叫法更直白 / same as ./install.sh
./install.sh check              # 逐字节比对：全 [OK] = 已是最新 / byte-compare against this clone
./install.sh check-remote       # 不克隆也能查：远端 commit vs 你安装时记下的 commit
```

- `check-remote` 读安装时写下的 `SOURCE`（`repo` / `ref` / `commit`），用 `git ls-remote` 问远端：退出码 `0` 已是最新、`3` 不一致（通常是你落后）、`1` 连不上远端。装的是加这个功能之前的版本（没有 `SOURCE`）时，它会直接告诉你怎么走兜底。
- 重跑会覆盖脚本、保留 `config.json` / `state.db` / `runs/` / `logs/`（这些是运行数据，被 `--exclude` 保护），crontab 那一行是幂等的。
- ⚠️ 升级后不需要重启 cron（每分钟一行，下一分钟就是新脚本）；但如果 `config.json` 新增了字段，脚本会打印提示，按提示补。

**English.** `install.sh` is idempotent, so **re-running it is the upgrade** — the payload is replaced wholesale. `check` byte-compares your install against the clone you are running from; `check-remote` needs no clone: it reads the `SOURCE` recorded at install time (`repo` / `ref` / `commit`) and asks the remote with `git ls-remote` (exit `0` up to date, `3` differs — usually you are behind, `1` remote unreachable). A copy installed before this feature has no `SOURCE` and says so, pointing at the fallback.

- Re-running overwrites the scripts and keeps `config.json` / `state.db` / `runs/` / `logs/` (runtime data, protected by `--exclude`); the crontab line is idempotent.
- ⚠️ No cron restart needed after an upgrade (the line runs every minute, so the next tick picks up the new scripts); if `config.json` gained fields the script says so — fill them in as prompted.

## 5. 配置 / Configuration

### 5.1 `config.json`

首次运行会自动从 `config.example.json` 生成。**注意路径是安装位置**：`~/.agents/tools/jira-devin-bot/config.json`（不是你在 repo 里看到的那份；`install.sh` 会把完整路径打给你）。

| 字段 | 说明 |
| --- | --- |
| `repo_dir` | **调度器在哪个项目里改代码** —— 目标项目的路径。⚠️ **不是本工具所在的仓库**（本工具是通用的，不会自动猜）。**必填**，留空时收到 `@AI` 会直接报错 |
| `jql` | **候选集合**。决定"哪些工单会被检查评论"。**多人部署时务必带 `assignee = currentUser()`** |
| `poll_interval_seconds` | 实际轮询间隔（cron 每分钟唤醒，内部节流），默认 300 |
| `devin_bin` | devin 可执行文件路径。**默认留空 = 自动查找**：先看这里，再依次找 `~/.local/bin/devin`、`/usr/local/bin/devin`，取**第一个「存在且已登录」**的（所以一台机器上有多个 devin 时不会卡在没登录那个）。都没找到才报错，工单保持 `queued`。<br>**装完请确认用的是哪个**：`install.sh` 会把它打出来，**本机存在多个时会列出其它候选**并提示；`./install.sh check` 也会显示。要换就把路径写进这个字段 |
| `permission_mode` | 传给 devin 的 `--permission-mode`，默认 `dangerous`（非交互模式必须显式给，否则 write/exec 会被拒） |
| `skill` | **用哪个 skill 响应 `@AI`** —— 逐项目的决定，本工具不绑定任何 skill。填 skill 名（如 `jira-fix-verify`）就走该 skill 的流程；**留空**则只让 agent 自行处理 |
| `device_id` | 测试设备名，对应 `.devin/config/global-config.local.json` 里 `devices` 的键。留空则要求 AI 向人类询问 |
| `comment_prefix` / `reply_prefix` | 默认 `[Generated by AI]` / `@AI` |
| `max_run_seconds` | 单次 devin 运行上限，超时会被 kill |
| `summary_enabled` | 流程完成后是否追加「任务结论」评论，默认 `true` |
| `summary_word_limit` | 结论字数上限，默认 `300`（**只写进 prompt 交给模型自己控制**，不硬截断） |
| `summary_timeout_seconds` | 生成结论那一次调用的超时，默认 600 |
| `log_retention_days` | 程序日志保留天数，默认 7 |
| `state_db` | sqlite 状态文件名 |

推荐 JQL（**装完必须手动改，否则不会触发任何工单**；多人隔离的关键）：

```
project = EGS00 AND assignee = currentUser() AND labels = ai-auto
```

**`repo_dir` 必须显式配置**：它是**目标项目**的路径，不是本工具所在的仓库 —— 本工具是通用的，装在 ai-toolbox 里、却要去别的项目里干活，所以它不会（也不该）自动推导。

**English.** `config.json` is generated from the example on first run and is gitignored. The JQL above is the recommended shape: `assignee = currentUser()` is what keeps concurrent installs from colliding. `repo_dir` must be set explicitly — it is the **target project**, not the repo this tool lives in, so it is never derived.

### 5.2 JIRA 凭证 / Credentials

放在 **`~/.config/windsurf/jira_config.json`**（与 `jira` skill 共用同一份解析逻辑）。优先级：环境变量（`JIRA_URL` / `JIRA_USER` / `JIRA_TOKEN` / `JIRA_AUTH_TYPE`）→ 该文件 → 仓库内 skill 的本地配置。

```json
{
  "jira_url": "https://<你的 jira>",
  "jira_user": "<账号ID>",
  "jira_token": "<PAT>",
  "jira_auth_type": "bearer",
  "ssl_verify": false,
  "timeout": 30
}
```

> **不要把 token 写进任何仓库。**

**English.** Credentials live in `~/.config/windsurf/jira_config.json`, shared with the `jira` skill; env vars take precedence. Never commit a token.

### 5.3 crontab

`./install.sh` **已经自动装好**了这一行（想跳过就加 `--no-cron`）：

```
* * * * * <repo>/tools/jira-devin-bot/tick.sh >> <repo>/tools/jira-devin-bot/logs/cron.log 2>&1
```

- cron 每分钟唤醒一次；**真实轮询间隔**由 `poll_interval_seconds` 节流；
- 日志每天滚动，按 `log_retention_days` 保留；
- 想停掉：`./install.sh uninstall --yes`（只移除 cron 行，配置与运行数据保留）。

**English.** `./install.sh` already installs that line (`--no-cron` skips it). Cron wakes the scheduler every minute; the real poll interval is throttled by `poll_interval_seconds`. Logs roll daily and are pruned by `log_retention_days`. To stop it: `./install.sh uninstall --yes` — it removes only the cron line and keeps your config and data.

## 6. 出问题怎么 debug / Troubleshooting

| 症状 / Symptom | 原因 / Cause | 处理 / Fix |
| --- | --- | --- |
| `missing command: flock` / `missing module: requests` | 依赖没装 | 按脚本打印的安装命令装好重试 |
| `devin binary not found` | `config.devin_bin` 路径写错 | 确认 `ls -l` 能列到该文件 |
| `... is not usable: auth status did not report a logged-in session` | Devin CLI 未登录 | 跑 `devin auth login`。**注意**：在 Devin Desktop 的终端里，`ACP_BACKEND=windsurf` 会让 CLI 显示未登录（认证交给宿主）；用 `env -u ACP_BACKEND devin auth status` 复核 |
| 报错后工单一直不动 | 设计如此 | setup 类错误**不消费工单**，工单保持 `queued`，修好后下一轮自动重试 |
| 打了 label 但 bot 完全不动 | 三个条件没凑齐 | 检查：指派给你 + 有 `ai-auto` label + 一条**你自己写的**以 `@AI` 开头的评论 |
| 别人的 `@AI` 触发了我的 bot | 作者过滤没生效 | 确认 `poll.find_work` 收到了 `me_name`（来自 `jira.myself().name`） |
| 同一工单被反复重跑 | 同一条 `@AI` 评论被重复消费 | 检查运行结束后 `last_consumed_comment_id` 是否推进到了该评论 id |
| AI 看到"人类回复为空" | 模板按"有无触发评论"选择 | 若出现说明触发路径异常，检查 `poll.py` 的 reply 检测 |
| 运行卡住 | 长任务 | `pgrep -af runner.py`；`runner.py` 持 `run.lock`，`max_run_seconds` 会兜底 kill |
| `poll.py` 报 JIRA 401 | token 过期 | 更新 `~/.config/windsurf/jira_config.json` |
| 想反悔 / 停掉 | — | 移除工单的 `ai-auto` label（= 退出管辖）；或注释掉 crontab 那一行 |

**English.** The table above maps each symptom to its cause and fix. The two most common ones: a missing dependency (install it and retry) and the Devin CLI reporting "not logged in" merely because it was checked from inside the Devin Desktop terminal (`ACP_BACKEND=windsurf` defers auth to the host — re-check with `env -u ACP_BACKEND devin auth status`).
