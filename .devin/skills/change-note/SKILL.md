# change-note

产出一份本地说明文件，回答「这处为什么改」。它**不替代** commit message，也**不替代** Gerrit description —— 那两个是给流程看的，这份是给你 review 时看的。

## 这是什么 / What this is

一个「让 AI 交代自己改了什么、为什么改」的 skill。它按逻辑单元组织说明，每个单元回答必要性 / 取舍 / 边界 / 风险与验证四问，最后用脚本核对 `git diff` 里的每个文件都在说明里出现过。

## 核心原则（先读这段，它决定了后面每一步）

1. **只读，不改代码**。这个 skill 唯一会写的文件是 `.devin/reviews/` 下的说明。
2. **覆盖每一个改动文件**。说明的 `## 文件覆盖表` 里必须写**仓库相对路径**；脚本会拿 `git diff --name-only` 逐个核对表里的路径，漏了就报。这是唯一能机械验证的部分，不要让人来发现遗漏。
3. **必要性必须可证伪**。不写「为了健壮性 / 更安全 / 防止异常」，写「不改 → `<哪条路径 / 哪个调用方 / 哪种输入>` 会 `<什么后果>`」。**写不出具体路径，说明这处改动本来就不该有** —— 这时要在「边界」里如实标成顺手改的，而不是编一个理由。
4. **按逻辑单元，不按文件**。5–10 组为宜；一组 = 一个说得清的意图，可以横跨多个文件，也可以只是某个文件里的一段。
5. **定位为主，追溯为辅**。先写「最该看的 N 处」和「文件覆盖表」，四问可以短。你的读者是 review 当时的人，不是三个月后考古的人。
6. **不阻断**。覆盖率脚本只报告，不卡提交；缺了就在说明里标出来，由人决定。

## 依赖 / Prerequisites

无外部依赖，只用 `git` 和 `python3`。

脚本：`scripts/check_coverage.py`（相对本 skill 目录）。在本仓里是 `.devin/skills/change-note/scripts/check_coverage.py`。

## 流程

### 第 0 步：确定范围

```bash
python3 .devin/skills/change-note/scripts/check_coverage.py --list
```

输出本次改动的文件清单和基线。基线按顺序自动取第一个非空的：

1. `git diff --name-only HEAD` —— 工作区 + 暂存区 vs HEAD（写说明时通常还没提交，走这条）
2. `git diff --name-only <merge-base>` —— 相对上游分支的整个 change（已提交 / amend 后走这条）
3. `git diff --name-only HEAD~1` —— 只有一个已提交 commit 时兜底

**清单为空就停下**，告诉用户「没有可说明的改动」，不要编。

### 第 1 步：读 diff

对每个改动文件读 `git diff`；「必要性」要落到调用路径上时，读改动前后的完整函数或调用方，**不要只读 diff 就下结论**。

### 第 2 步：划分逻辑单元

把改动归成 5–10 组，分组标准是**意图**，不是目录：

- 「新增 X 能力」「为 X 改调用方」「为 X 补测试」是三个单元，哪怕都在同一个文件里。
- 「顺手补的空值保护」必须单独成一个单元 —— 它最容易被藏进别的单元里。

超过 10 组，说明改动该拆；少于 2 组且改动文件超过 5 个，说明切得太粗。

### 第 3 步：写说明

路径：`.devin/reviews/<YYYY-MM-DD-HHMM>-<slug>.md`。`slug` 从任务名取，小写 ASCII、连字符分隔，如 `2026-10-27-1530-jira-confluence-write`。

用下面的模板。`## 覆盖检查` 一节**先留空**，第 4 步由脚本填。

### 第 4 步：核对覆盖率

```bash
python3 .devin/skills/change-note/scripts/check_coverage.py --note .devin/reviews/<文件名>
```

脚本把结果打印到终端，并回写说明里的 `## 覆盖检查` 一节。**有遗漏就回到第 3 步补进 `## 文件覆盖表`**，不要把遗漏留给人。

### 第 5 步：汇报

只回三行：文件路径、覆盖 N/M、最该看的 1 处。不要把说明全文贴进会话 —— 它是文件，不是聊天记录。

## 模板

````markdown
# 改动说明 — <任务名>

- **日期**：YYYY-MM-DD HH:MM
- **范围**：N 个文件，+X / -Y 行
- **基线**：<脚本给出的基线>

## 摘要

<3 行：改了什么、为什么、最该看哪>

## 最该看的 N 处

1. `path/to/file.c`（`func_name`）— <为什么这里最值得看：最容易错 / 最影响别人 / 最不显然>
2. `path/to/other.py`（`ClassName.method`）— <…>

## 逻辑单元

### U1 <名字>

**涉及**：`path/a.c`（`func_a`）、`path/b.h`

- **必要性**：不改 → `<哪条路径 / 哪个调用方 / 哪种输入>` 会 `<什么后果>`。
- **取舍**：考虑过 <方案 B>，否掉因为 <原因>；<没有替代方案就写「无」>。
- **边界**：`path/b.h` 的 `#include` 是顺手加的，因为 <原因>；<没有就写「无」>。
- **风险与验证**：<哪里最可能错>；测了 <什么>；<哪些是没验证的假设>。

### U2 <名字>

**涉及**：`path/c.py`

- **必要性**：…
- **取舍**：…
- **边界**：…
- **风险与验证**：…

## 文件覆盖表

| 文件 | 单元 | 类型 |
| --- | --- | --- |
| `path/a.c` | U1 | 核心 |
| `path/b.h` | U1 | 顺手 |

类型只有三种：`核心`（不改成不了事）、`连带`（核心改动的直接后果）、`顺手`（看到了就一起改）。**脚本不校验这一列** —— 它是给你跳读用的，别指望它证明什么。

## 覆盖检查

## 修订记录

<第一次生成时删掉这一节>
````

## amend 之后

Gerrit 流程里 amend 很常见，说明会和 diff 对不上。**不要重新生成整份** —— 那会丢掉「当初为什么那么做」。

在第 3 步补完新的 diff 覆盖后，往 `## 修订记录` 追加一段：

```markdown
### YYYY-MM-DD HH:MM — <一句话：这次改了什么>

- 改了什么：<…>
- 为什么：<回应哪条 review finding，或发现了什么新问题>
- 影响到的单元：U2、U4
```

然后重跑第 4 步，让 `## 覆盖检查` 反映最新基线。

## 失败处理

| 情况 | 怎么办 |
| --- | --- |
| 改动清单为空 | 停下，告诉用户没有可说明的改动。不要为了产出而编。 |
| 不在 git 仓库 | 脚本退出码 `2`；报告并停下，不要手搓 diff。 |
| 说明文件不存在 | 脚本退出码 `2`；先按第 3 步创建。 |
| `--base` 无效 | 脚本退出码 `2`；先用 `git rev-parse --verify <ref>^{commit}` 检查 ref 是否存在，不要当成「没有改动」。 |
| `## 文件覆盖表` 缺失 / 表里没有该文件 | 脚本会把该文件报成「未覆盖」；回到第 3 步把文件补进表里。 |
| 覆盖率有遗漏 | 回到第 3 步补，**不要把遗漏留给人**。 |
| 单元数 > 10 | 如实告诉用户「这次改动该拆」，并给出拆分建议；不要硬压成 10 组。 |
| 写不出可证伪的必要性 | 这处改动多半是顺手的 —— 如实标成「顺手」，别编理由。 |

## 安全与禁止事项

- **不修改任何源文件**。这个 skill 的写权限只到 `.devin/reviews/`。
- **不伪造理由**。必要性写不出具体路径，就是没有必要性；标成「顺手」比编一个「为了健壮性」诚实得多。
- **不把说明全文贴进会话**。汇报只回三行。
- **不改 `.gitignore` 之外的本仓配置**。`.devin/reviews/` 已被忽略，说明不进仓。
